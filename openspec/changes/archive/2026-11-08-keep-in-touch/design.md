# Design

## Context

Что есть сейчас (см. `proposal.md` - зачем это нужно):

- Таблица `contacts` - имя, «кто это», «откуда знакомы», телефон, почта, даты создания и изменения. Таблица `notes` - текст и дата создания, привязана к контакту. Индекс `notes_contact_id_created_at_idx` уже позволяет быстро найти последнюю заметку контакта.
- Заметки можно только добавлять: изменить или удалить отдельную заметку нельзя. Значит, «последняя заметка» меняется только при добавлении новой.
- Главная (`src/app/page.tsx`) - сверху закреплённая шапка с заголовком, кнопкой «Добавить контакт» и поиском, ниже список. Список и счётчик читаются в одном асинхронном компоненте `ContactList` внутри `Suspense` (пока данные грузятся, виден скелетон - серые заглушки).
- Форма контакта (`src/components/contact-form.tsx`) - общая для добавления и изменения, поля описаны массивом `FIELDS`, значения читаются из `FormData`. Проверка - `contactInputSchema` (zod) в `src/lib/contacts/validation.ts`, она же работает в серверных действиях `createContact` / `updateContact`.
- Сохранение заметки (`addNote`) обновляет кэш только страницы карточки, главную - нет.
- Компонентов выбора (select) в `src/components/ui/` пока нет. Стиль shadcn - `base-nova`, компоненты работают на Base UI (`@base-ui/react` уже установлен).
- Модульных тестов нет, есть только сквозные (Playwright, `pnpm test:e2e`): они работают с той же базой, что и приложение, и сами готовят данные SQL-запросами.
- Макет экранов (компьютер и телефон): https://claude.ai/artifact/BaEDM8gJCb952y6rwfK6wr - главная с блоком, карточка, форма «Изменить контакт». Вёрстка блока, плашки частоты и кнопки «Связались» - по нему; цвета и шрифты на макете - те же токены приложения.

## Goals / Non-Goals

**Goals:**

- Решение «пора / не пора» и порядок блока считаются в одном запросе к базе: без загрузки всех контактов и заметок в приложение.
- Изменение схемы только добавляет поля: старый образ приложения продолжает работать с новой базой, ручной откат образа остаётся безопасным.
- Блок не вызывает скачков вёрстки при загрузке главной.

**Non-Goals:**

- Отдельная страница или адрес для «Пора связаться».
- Показ даты следующего общения в карточке.
- Удаление заметок: отменить можно только только что сохранённую «Связались» (решение 7).
- Исправление часового пояса в датах по всему приложению (см. Risks).

## Decisions

### 1. Данные: два поля в `contacts`

- `contact_frequency` - перечисление Postgres `contact_frequency` со значениями `week`, `month`, `quarter`, `year`; пусто (`null`) = «Не задано».
- `contact_frequency_set_at` - момент, когда частоту задали или сменили (`timestamptz`); пусто, если частота не задана.

Почему перечисление, а не просто текст: база сама не даст сохранить неизвестное значение, а Drizzle выводит из него тип для TypeScript. Добавить значение позже - одна команда миграции.

Почему не отдельная таблица «касаний»: общение = заметка, а заметки уже хранятся. Отдельная история касаний понадобится, только если появится «связался без заметки» - этого нет в требованиях.

Миграция генерируется `pnpm db:generate` (Drizzle) и только добавляет тип и два пустых поля - существующие строки не трогаются.

### 2. Когда сдвигается `contact_frequency_set_at`

- Добавление контакта: если частота выбрана - `now()`, иначе пусто.
- Изменение контакта: в одном `UPDATE` через `CASE` по старому значению поля. Частота не изменилась - поле не трогаем; сменилась на другую - `now()`; стала «Не задано» - пусто. Сравнение идёт в самой базе, поэтому нет гонки «прочитал старое значение - записал новое».

Почему не сдвигать при каждом сохранении формы: тогда правка телефона у контакта без заметок отодвигала бы срок - это противоречит требованию.

### 3. Расчёт срока - в SQL

Новая функция `listDueContacts()` в `src/lib/contacts/queries.ts`:

- берёт контакты с заданной частотой;
- для каждого через `LEFT JOIN LATERAL` находит последнюю заметку (дата, первая строка текста, не длиннее 200 символов) - это использует уже существующий индекс;
- начало отсчёта = `coalesce(дата последней заметки, contact_frequency_set_at)`;
- конец срока = начало + интервал: `week` → `7 days`, `month` → `1 month`, `quarter` → `3 months`, `year` → `1 year`. Сложение дат с интервалом в месяцах Postgres делает по календарю (15 сентября + 1 месяц = 15 октября);
- оставляет строки, где конец срока ≤ `now()`;
- считает число полных суток просрочки: `floor(extract(epoch from now() - конец срока) / 86400)`; 0 - «Пора сегодня». Сутки - ровно 24 часа от момента окончания срока, поэтому часовой пояс на число не влияет;
- сортирует по концу срока (самый ранний - самый просроченный - сверху), при равенстве - по имени.

Соответствие частоты и интервала хранится в коде в одном месте рядом со списком значений и подписей.

Альтернатива - считать в JavaScript: пришлось бы читать все контакты с частотой и их последние заметки. Запрос проще и быстрее, а «сейчас» берётся из одних часов - часов базы.

### 4. «Показать всех» - на стороне браузера

Сервер отдаёт все просроченные контакты разом. Небольшой клиентский компонент `KeepInTouchList` показывает первые 5 и кнопку «Показать всех (N)»; по нажатию показывает всех, кнопка исчезает.

Почему так: строки маленькие (имя, дата, одна строка заметки), даже сотни строк - пустяк. Альтернативы - параметр в адресе (`?due=all`, лишняя перезагрузка данных) или догрузка по кнопке (лишний запрос и состояние загрузки) - сложнее без пользы.

### 5. Место блока на главной

Блок рендерится внутри того же `ContactList` (тот же `Suspense`) - между шапкой с поиском и строкой «Всего N контактов». Запрос `listDueContacts()` идёт параллельно со списком (`Promise.all`), и только когда поиск пуст. Так скелетон загрузки общий: блок не «выпрыгивает» над уже показанным списком.

Строка блока (как на макете): аватар (как в списке), имя - ссылка на карточку на всю строку (как в списке: невидимый слой ссылки растянут поверх строки), под именем «Просрочено на 24 дня (последняя заметка 15 сентября 2026 г.)», «… (заметок нет)» или «Пора сегодня (…)», начало заметки в одну строку с многоточием и кнопка «Связались» справа. Кнопка стоит не внутри ссылки (кнопка внутри ссылки - ошибка разметки), а рядом и поверх слоя ссылки, поэтому нажатие на неё карточку не открывает. Число дней с окончанием слова - через существующий `pluralize` из `src/lib/format.ts`. Строки блока не получают `id` строк основного списка (`contactRowId`), чтобы прокрутка к новому контакту продолжала находить строку в списке.

Внешний вид - карточка `bg-card` с заголовком «Пора связаться», только существующие дизайн-токены. Заголовок блока - `h2`, для доступности секция подписана этим заголовком.

### 6. Частота в форме и карточке

- Форма: новое поле «Как часто общаться» после «Почты» - выпадающий список (`Select` из shadcn/ui, добавляется командой `pnpm dlx shadcn@latest add select`; это компонент поверх уже установленной Base UI, не новая библиотека). Значения: «Не задано», «Раз в неделю», «Раз в месяц», «Раз в квартал», «Раз в год». У `Select` Base UI есть скрытое поле с `name`, поэтому чтение формы через `FormData` не меняется.
- Проверка: `contactInputSchema` получает поле `contactFrequency`: пустая строка → `null`, иначе одно из четырёх значений; неизвестное значение - ошибка поля.
- Карточка: в шапке под «Кто это» плашка с иконкой «Общаемся раз в месяц» и рядом кнопка «Связались» (та же, что в блоке). Кнопка «Связались» нужна только при заданной частоте; при «Не задано» на месте плашки кнопка «Задать частоту», а «Связались» нет. Четыре плитки (откуда знакомы, телефон, почта, в списке с) не трогаем - пятая плитка сломала бы сетку 2×2.
- Плашка - кнопка выбора частоты: тот же `Select`, что в форме, только вместо поля - плашка (тот же вид, плюс стрелка вниз), а при «Не задано» - кнопка «Задать частоту». Список и отметка выбранного - как в форме. Выбор сразу вызывает серверное действие `updateContactFrequency(contactId, frequency)`: та же проверка значения, что в `contactInputSchema`, и тот же `CASE` для `contact_frequency_set_at`, что в `updateContact` (решение 2) - он выносится в общую функцию, чтобы правило «когда сдвигать срок» было в одном месте. Действие обновляет кэш главной и карточки. Пока сохраняется, кнопка неактивна; карточка перерисовывается с новым значением с сервера. Ошибка (в том числе оборванный запрос) - сообщение с текстом ошибки сохранения, частота прежняя. Отдельного сообщения об успехе нет - надпись меняется на глазах.

### 7. Кнопка «Связались»

- Серверное действие `markContacted(contactId)` в `src/app/contacts/actions.ts` сохраняет обычную заметку с текстом «Связались» (константа рядом с другими текстами действий) той же вставкой, что и `addNote`, и обновляет кэш главной и карточки. Новых полей и таблиц нет: срок и дата в скобках по-прежнему считаются от последней заметки.
- Клиентский компонент `MarkContactedButton` - один и в строке блока, и в карточке. Пока идёт сохранение, кнопка неактивна, а второе нажатие игнорируется (тот же приём, что в `AddNoteForm`, - защита от двух одинаковых заметок). Успех - сообщение «Заметка «Связались» сохранена» (sonner, как у заметок). Ошибка - сервер вернул ошибку или запрос не дошёл - сообщение с текстом ошибки сохранения, контакт остаётся в блоке.
- Отклонённая альтернатива: отдельное поле «когда отметили» без заметки. Владелец выбрал заметку: у «последнего общения» один источник, и дата в скобках всегда верная.
- «Отменить»: `markContacted` возвращает id сохранённой заметки. Сообщение об успехе (sonner) получает кнопку «Отменить» и живёт 10 секунд вместо обычных 4 - так же устроена кнопка «Открыть» в сообщении «Контакт добавлен». Нажатие вызывает серверное действие `undoMarkContacted(contactId, noteId)`, которое удаляет заметку, только если она принадлежит этому контакту, её текст «Связались» и сохранена меньше минуты назад (по часам базы). Без этих условий действие можно было бы вызвать напрямую и стереть любую заметку; минута вместо 10 секунд - запас на медленную связь. Удалить не вышло (база недоступна, запрос оборван, условия не выполнены) - сообщение «Не удалось отменить: заметка «Связались» осталась. Проверьте, что база данных запущена.» Действие обновляет кэш главной и карточки: контакт возвращается в блок, заметка пропадает из карточки. Отмена удаляет заметку - срок снова считается от предыдущей заметки, как будто нажатия не было.

### 8. Обновление главной после заметки

`addNote`, `markContacted`, `undoMarkContacted` и `updateContactFrequency` вызывают `revalidatePath("/")`. Next.js сбрасывает кэш главной, и при переходе «Все контакты» блок уже без этого контакта; нажатие в самом блоке перерисовывает главную сразу. `createContact` и `updateContact` главную уже обновляют.

### 9. Проверки

- Новый сквозной тест `e2e/keep-in-touch.spec.ts`. Готовит контакты SQL-запросами с датами в далёком прошлом (1990-е), чтобы они были самыми просроченными в любой базе, и удаляет их в конце. Проверяет: порядок по просрочке, строку с заметкой и без, число дней с окончаниями и «Пора сегодня», «Показать всех», скрытие при поиске, частоту в форме и карточке, уход из блока после заметки, «нет заметок - срок от момента, когда задали частоту» (контакт с частотой, заданной 8 дней назад, «раз в неделю» - в блоке; заданной сегодня - нет). Кнопка «Связались»: из блока - контакт уходит, страница остаётся главной, в базе новая заметка «Связались»; из карточки - заметка сверху, счётчик +1; при «Не задано» кнопки нет; двойное нажатие - одна заметка; ошибка - тест обрывает запрос действия (`page.route`), контакт остаётся в блоке. «Отменить»: из блока - контакт вернулся, заметки нет в базе; из карточки - заметка пропала, счётчик прежний; через 10 секунд кнопки нет; оборванный запрос отмены - сообщение, заметка в базе осталась. Частота из карточки: смена, «Задать частоту», «Не задано», выбор той же частоты не сдвигает `contact_frequency_set_at`.
- Тестовые данные `pnpm db:seed`: части контактов (около 15%) назначается частота, чтобы на свежей базе блок был виден сразу. На уже заполненной базе сид ничего не делает - как и сейчас.
- Существующие тесты ищут ссылку на контакт по имени. Их контакты без частоты, в блок не попадут - двойных ссылок не будет. Прогнать их все после изменений.

## Risks / Trade-offs

- [Один контакт виден дважды на главной - в блоке и в списке] → Это ожидаемо по требованиям; в тестах искать ссылку внутри нужной секции (`Пора связаться` / `Список контактов`).
- [Случайное нажатие «Связались» заметили позже 10 секунд] → Заметку уже не удалить; удаление заметок - отдельная доработка, если понадобится.
- [Выбор частоты в карточке сохраняется сразу, без кнопки «Сохранить»] → Ошибочный выбор исправляется так же - повторным выбором; если частоту меняли, а заметок нет, срок начнётся с момента последнего выбора, как и при сохранении формы.
- [Кнопка поверх ссылки на всю строку: легко сломать так, что нажатие откроет карточку] → Отдельный сценарий в тесте: после нажатия адрес остаётся главной.
- [Часовой пояс: сервер в Docker живёт по UTC, даты заметок форматируются по часам сервера - около полуночи по Москве дата может отличаться на день] → Так уже работает вся карточка, блок ведёт себя так же. Сам момент «пора» от часового пояса не зависит (сравниваются моменты времени). Отдельное исправление - вне этой фичи.
- [Месяц по календарю: 31 января + 1 месяц = 28/29 февраля] → Так считает Postgres; для напоминаний разница в пару дней не важна.
- [Очень много просроченных - все приходят в браузер разом] → При 1000 контактов это десятки килобайт; если станет заметно, перейти на догрузку по кнопке.
- [Перечисление в базе: значения сложно удалять] → Удалять не планируется; добавить новое - простая миграция.

## Migration Plan

1. Миграция `0001_*` только добавляет тип `contact_frequency` и два пустых поля в `contacts`. Выполняется обычным шагом выкатки - разовым контейнером до старта нового образа.
2. У всех существующих контактов частота «Не задано» - блок «Пора связаться» на проде пуст, пока пользователь не задаст частоты.
3. Откат (вручную, запускает владелец): вернуть предыдущий образ. Старый код не знает о новых полях и просто их не читает - база откатывать не нужно.
