# Design

## Context

Зачем фича - см. proposal.md; что должно работать - `specs/sign-in/spec.md`, `specs/data-ownership/spec.md`, изменения групп - `specs/contact-groups/spec.md`. Требования владельца - `specs/02-пользователи-вход.md`.

Решения владельца на этапе плана (2026-11-10):

- почта владельца для уже существующих данных и демо-данных - из настройки `OWNER_EMAIL`, не из кода: репозиторий на GitHub публичный;
- каждый новый пользователь получает свои пустые «Семья», «Друзья», «Коллеги»;
- все тексты на «вы», как во всём приложении: «Проверьте адрес почты», «Ссылка устарела, запросите новую», «Слишком часто, попробуйте через несколько минут»; новому пользователю и для чужого контакта - уже существующие экраны «Пока нет ни одного контакта» и «Такого контакта нет»;
- адрес отправителя на сервере - `noreply@mail.personalcrm.site`.

Решения владельца после обзора фичи (2026-11-10):

- заголовок страницы входа - «Вход в Личную CRM»;
- письмо не удалось отправить - «Не удалось отправить письмо. Попробуйте ещё раз через пару минут.»;
- с одного устройства - вход не больше чем на 5 разных адресов за любой час, дальше - «С этого устройства запрашивали вход на слишком много адресов. Попробуйте позже.». Устройство - адрес в интернете (IP), одна домашняя сеть - одно устройство.

Макет экранов (компьютер и телефон), согласован владельцем: https://claude.ai/artifact/6u3yPGZbWeBWTa14dhcJ4r - страница входа, состояния формы (все ошибки и «Ссылка отправлена»), страница «Ссылка устарела», шапка с почтой и «Выйти», письмо. Вёрстка - по нему; цвета и шрифты - токены приложения. На телефоне почта в шапке идёт второй строкой под логотипом и «Выйти», длинная обрезается многоточием. Первая строка письма - «Чтобы войти, нажмите кнопку. Ссылка работает 15 минут и открывается один раз.» Ссылка открывается только у владельца, пока её не расшарили.

Как устроено сейчас (на что опирается подход):

- Next.js 16 с `cacheComponents: true`: всё, что читает запрос (cookies, заголовки), должно быть внутри `<Suspense>`, иначе сборка падает. Страницы уже так устроены: данные читаются в компонентах внутри `Suspense`, функции запросов вызывают `connection()`.
- Чтение - `src/lib/contacts/queries.ts`, `src/lib/groups/queries.ts`; запись - серверные действия `src/app/contacts/actions.ts`, `src/app/groups/actions.ts`, общие `src/lib/groups/mutations.ts`. Ни одна функция сейчас не знает о пользователе.
- В базе `contacts`, `notes`, `groups`, `contact_groups`. Уникальность названия группы - индекс `groups_name_unique_idx` по `translate(lower(name), 'ё', 'е')` на всю таблицу. Миграция `0003` вставляет три готовые группы без владельца - поэтому даже свежая база (CI, новый компьютер) после `0003` уже не пустая.
- Миграции: локально `pnpm db:migrate` (drizzle-kit), на сервере - разовый контейнер `node scripts/migrate.mts`; Vitest применяет их сам в `test/global-setup.ts`, тесты миграций - через `test/migrations.ts`.
- Тесты Vitest подменяют только `next/cache` и `next/server`; база настоящая. e2e (Playwright) работают с рабочей локальной базой, сами вставляют тестовые контакты прямым SQL и проверяют главный сценарий на заполненном списке (CI выполняет `pnpm db:seed`).
- На сервере `deploy/compose.yaml` передаёт приложению только `DATABASE_URL`, собранный из `POSTGRES_*` в `.env`. Прод-база заполнена тестовыми данными (1000 контактов).
- Перед приложением на сервере стоит nginx (`/etc/nginx/sites-available/personalcrm.conf`, блок `app.personalcrm.site` - наш), он передаёт запросы на `127.0.0.1:3000`. Передаёт ли он адрес устройства, при планировании проверить не удалось: чтение с сервера требует разрешения владельца. Сам Next.js, если заголовка нет, ставит в `x-forwarded-for` адрес соединения - на сервере это адрес Docker, одинаковый для всех.
- `.env` и `.env.example` агенту недоступны (запрет в настройках) - строки туда добавляет владелец.

## Goals / Non-Goals

**Goals:**

- Каждый запрос к данным знает текущего пользователя и физически не может вернуть или изменить чужую запись: условие «владелец = я» в каждом запросе, проверка на сервере, а не в интерфейсе.
- Миграция назначает владельца всем существующим записям, ничего не теряя; без `OWNER_EMAIL` она останавливается, ничего не меняя.
- Письма уходят через Nodemailer по SMTP; куда - заглушка Mailpit или Resend - решает только `.env`.
- У каждого сценария спек - свой автотест (Vitest для серверной части, Playwright - для того, что видно на экране); исключение - сценарии про настоящие письма на сервере, их проверяем настоящей выкаткой.

**Non-Goals:**

- Всё из «Не делать» в `specs/02-пользователи-вход.md`: пароли, соцсети, код из письма, профиль, смена почты, удаление аккаунта, общий доступ, приглашения, роли, админка.
- Различать устройства внутри одной сети (по cookie или «отпечатку» браузера): программа-рассыльщик cookie не хранит, а владелец согласился считать одну сеть одним устройством.
- Кэширование данных пользователя (`use cache`) - приложение и сейчас читает всё при каждом запросе.

## Decisions

### 1. Better Auth: настройка

- Библиотека `better-auth` (последняя стабильная на момент установки; при планировании - 1.7.19), плагины `magicLink` и `nextCookies` (последний - чтобы серверные действия могли ставить и стирать cookie входа). Адаптер Drizzle, `usePlural: true` - таблицы `users`, `sessions`, `accounts`, `verifications`, как наши `contacts`, `groups`. Идентификаторы - `uuid`, как у остальных таблиц (`advanced.database.generateId: "uuid"`).
- Схема этих четырёх таблиц пишется в `src/db/schema.ts` по образцу из Better Auth CLI (`@better-auth/cli generate`), имена столбцов - snake_case, как у нас; миграцию генерирует drizzle-kit. `accounts` для входа по ссылке не нужна, но Better Auth проверяет, что все его таблицы есть.
- Обработчик Better Auth - `src/app/api/auth/[...all]/route.ts` (`toNextJsHandler`). Через него идут переход по ссылке из письма (`/api/auth/magic-link/verify`) и прямые запросы.
- Настройки: `BETTER_AUTH_SECRET` (случайная строка, подписывает cookie) и `BETTER_AUTH_URL` (адрес приложения: `http://localhost:3000` локально, `https://app.personalcrm.site` на сервере). Ссылка в письме строится от `BETTER_AUTH_URL`.
- Сборка образа: как `DATABASE_URL`, на время `pnpm build` - заглушки, настоящие значения приходят при запуске.

Отвергнуто: свой вход «с нуля» - спека требует Better Auth; хранить вход в подписанном cookie без базы - тогда нельзя выйти только на одном устройстве надёжно и нельзя продлевать срок.

### 2. Ссылка из письма: срок, одноразовость, «новая отменяет старые»

Проверено по исходникам `better-auth@1.7.19`:

- Срок - `expiresIn: 15 * 60`. Одноразовость уже встроена: ссылка «расходуется» при первом переходе.
- Код ссылки в базе хранится не сам, а его отпечаток (`storeToken` со своей функцией SHA-256): украденная копия базы не даёт войти. Свою функцию, а не встроенный `"hashed"`, берём, чтобы самим вычислять, какая запись принадлежит текущей ссылке.
- «Новая ссылка отменяет старые» в Better Auth нет. Делаем в `sendMagicLink` (вызывается после того, как новая запись уже создана): после удачной отправки письма удалить из `verifications` все записи входа по ссылке для этой почты, кроме только что созданной. Запись Better Auth хранит почту в JSON (`{"type":"magic-link","email":...}`) - на этот формат опираемся, тест «Запросил новую ссылку» поймает, если он изменится при обновлении библиотеки.
- Переход по ссылке: `callbackURL: "/"`, `errorCallbackURL: "/login/expired"`. Любая ошибка (`INVALID_TOKEN` и другие) ведёт на страницу «Ссылка устарела, запросите новую» с кнопкой «Запросить новую ссылку» → `/login`. Различать причины не нужно: спека показывает один экран.

### 3. Проверка почты и лимит писем - в одном месте для формы и прямых запросов

- Правило почты - одна zod-схема `src/lib/auth/validation.ts`: обрезать пробелы, маленькие буквы, формат почты (`z.email()`, как у почты контакта), иначе «Проверьте адрес почты».
- Её применяет «before»-обработчик Better Auth (`hooks.before`) для пути `/sign-in/magic-link`. Такие обработчики, по исходникам, выполняются и для запросов из браузера, и для вызовов `auth.api.*` с сервера - значит, и форма, и запрос в обход формы проходят одну проверку. Обработчик подменяет почту в запросе на приведённую.
- Журнал для обоих лимитов: таблица `sign_in_emails` (`email`, `ip_address`, `created_at`) - одна строка на каждое отправленное письмо. Индексы `(email, created_at)` и `(ip_address, created_at)`.
- Адрес устройства: заголовок `X-Real-IP`, который ставит nginx (решение 13); нет его (локально, в автотестах) - адрес соединения, который Next.js кладёт в `x-forwarded-for`. Тот же порядок заголовков - во встроенном лимите Better Auth (`advanced.ipAddress.ipAddressHeaders`), чтобы оба лимита видели одно устройство.
- В том же обработчике, в одной транзакции, по порядку:
  1. блокировки по устройству и по почте (`pg_advisory_xact_lock`, всегда в этом порядке, чтобы два запроса не ждали друг друга вечно) - два одновременных запроса не проскочат лишним письмом;
  2. лимит устройства: эта почта не среди адресов, на которые с этого устройства ушли письма за последний час, а таких адресов уже 5 - ошибка «С этого устройства запрашивали вход на слишком много адресов. Попробуйте позже.»;
  3. лимит почты: на эту почту за последние 10 минут ушло 3 письма - ошибка «Слишком часто, попробуйте через несколько минут»;
  4. иначе - строка в журнал.
  Сработал лимит - ссылка не создаётся. Строки старше часа удаляются тут же - журнал не растёт, адреса устройств хранятся не дольше часа.
- Письмо не ушло (решение 5) - строка журнала и только что созданная ссылка удаляются: неудачная попытка не считается в лимиты, а старые ссылки ещё не тронуты (см. решение 2: они удаляются только после удачной отправки).
- Ошибки обработчик отдаёт как `APIError` с нашим кодом и русским текстом; прямой запрос получает их в ответе, форма - через серверное действие (решение 4).
- Встроенный в Better Auth лимит по устройству (5 запросов в минуту) действует только для запросов из браузера напрямую, не для серверного действия; оставляем его как есть.

Отвергнуто: встроенный лимит Better Auth вместо своих - он считает запросы, а спека - письма на почту и разные адреса с устройства. Проверка только в серверном действии - прямой запрос к `/api/auth/sign-in/magic-link` её обошёл бы. Устройство по cookie - рассыльщик его просто не хранит.

### 4. Страница входа и серверное действие

- `/login` (`src/app/login/page.tsx`): заголовок «Вход в Личную CRM», поле «Почта», кнопка «Получить ссылку». Форма вызывает серверное действие `requestSignInLink(email)` в `src/app/login/actions.ts`, как остальные формы приложения (`ActionResult`).
- Действие: проверка той же схемой (ошибка под полем без похода в Better Auth) → `auth.api.signInMagicLink({ body: { email, callbackURL: "/", errorCallbackURL: "/login/expired" }, headers })` → успех: «Ссылка для входа отправлена на <почта>» с приведённой почтой; наш `APIError` - его текст под полем.
- Ответ одинаковый для новой и знакомой почты: Better Auth и так не различает их при отправке.
- Сообщение об успехе появляется под формой, форма остаётся - можно запросить ещё раз (в пределах лимита).
- Уже вошедший пользователь, открывший `/login`, попадает на главную.

### 5. Письмо: Nodemailer по SMTP, адрес - из настроек

- `nodemailer` (последняя стабильная; при планировании - 10.5.0) и `@types/nodemailer`. Один модуль `src/lib/mail/` создаёт транспорт SMTP из настроек: `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD` (пустые - без логина), шифрование включается для порта 465. Адрес отправителя - `MAIL_FROM_ADDRESS`, имя «Личная CRM» - в коде (оно из спеки и одинаково везде).
- Локально и в CI: Mailpit, `SMTP_HOST=127.0.0.1` (в CI - `localhost`), `SMTP_PORT=1025`, без логина. На сервере: Resend по SMTP - `smtp.resend.com`, порт 465, пользователь `resend`, пароль - ключ Resend. Так «одна библиотека Nodemailer» и «решают настройки» выполняются буквально: в коде нет ветки «если сервер».
- Письмо - тема «Вход в Личную CRM», HTML с кнопкой «Войти» и текстовая версия, срок 15 минут, «Если вы не запрашивали вход - просто проигнорируйте письмо» - текст по спеке; содержимое собирает чистая функция, её проверяет тест.
- Ошибка отправки (почтовый сервер недоступен) - в лог, пользователю - «Не удалось отправить письмо. Попробуйте ещё раз через пару минут.» под полем; попытка не считается в лимиты (решение 3). Тест - с почтовым сервером на закрытом порту: настоящий сбой соединения, как в тестах «база недоступна».

Отвергнуто: отправка через API Resend (их библиотека) - спека требует Nodemailer, а через SMTP Resend работает с ним без второй библиотеки.

### 6. Mailpit локально и в CI

- `compose.yaml`: сервис `mailpit` (`axllent/mailpit`, конкретная версия - последняя стабильная при установке), порты только на `127.0.0.1`: 1025 (SMTP), 8025 (страница в браузере `http://localhost:8025`).
- CI (`ci.yml`, проверка «Tests»): сервис `mailpit` рядом с `db` и переменные: `BETTER_AUTH_SECRET` (тестовая строка), `BETTER_AUTH_URL`, `SMTP_*`, `MAIL_FROM_ADDRESS`, `OWNER_EMAIL=owner@example.com`, `MAILPIT_URL=http://localhost:8025`. Это не секреты: база и заглушка живут только на время проверки.
- Тесты берут письма через API Mailpit (`/api/v1/search`, `/api/v1/message/{id}`), помощник - `test/mailpit.ts`, общий для Vitest и Playwright. Перед тестом письма своей почты удаляются, чтобы не взять чужую ссылку.
- Все автотесты идут с одного адреса (`127.0.0.1`) и входят под многими почтами, поэтому перед каждым тестом журнал `sign_in_emails` очищается (Vitest и так очищает все таблицы, в Playwright - `beforeEach`). Лимит не выключается: тесты лимитов проверяют его по-настоящему, а разные устройства в них - разные значения `X-Real-IP`.

### 7. Сессия: 30 дней с последнего захода, закрытость без входа

- `session.expiresIn: 30 дней`, `session.updateAge: 1 час` - срок продлевается не чаще раза в час, то есть вход держится 30 дней с последнего захода с точностью до часа.
- Проверено по исходникам: когда страница рисуется на сервере, Better Auth срок не продлевает (cookie там записать нельзя). Поэтому продление - в `proxy.ts` (в Next.js 16 так называется прежний middleware, работает на Node.js): при открытии страницы (запрос документа, не фоновая подгрузка) вызывает проверку входа Better Auth и переносит обновлённое cookie в ответ. Фоновые подгрузки и переходы внутри приложения проверяют только наличие cookie, без базы - как советует документация Next.js.
- Проверено на настоящем dev-сервере и в собранном образе: продление срока из `proxy.ts` переносит cookie в ответ (запасной путь не понадобился). Переход на `/login` Next.js принимает только с полным адресом, поэтому он строится от `BETTER_AUTH_URL` (публичный адрес), а не от адреса запроса: за nginx тот может оказаться `127.0.0.1:3000`.
- `proxy.ts` же отправляет на `/login` всех без cookie входа. Открыты: `/login`, `/login/expired`, `/api/auth/*`, `/health`, статика.
- `proxy.ts` - не защита, а удобство. Защита - функция `getCurrentUser()` в `src/lib/auth/current-user.ts` («слой доступа к данным» из документации Next.js): читает вход через `auth.api.getSession({ headers })`, без входа - `redirect("/login")`. Её вызывают каждая страница (в компонентах внутри `Suspense`) и каждое серверное действие первой строкой.
- Выход - серверное действие `signOut()` → `auth.api.signOut` (удаляет только эту запись в `sessions`, остальные устройства остаются) → `redirect("/login")`.
- Шапка (`layout.tsx`): почта и «Выйти» - отдельный компонент внутри `Suspense`; без входа (страница входа) он ничего не рисует.

Отвергнуто: короткий кэш входа в cookie (`cookieCache`) - экономит запрос к базе, но «Выйти» на другом устройстве срабатывало бы с задержкой; для маленького приложения не нужно.

### 8. Владелец у данных

- `contacts.user_id` и `groups.user_id` → `users.id`, `not null`, `on delete restrict`: удаления пользователей в приложении нет, а случайное удаление строки пользователя не должно унести его контакты.
- У `notes` и `contact_groups` столбца владельца нет: заметка принадлежит контакту, связь - паре контакт и группа, и все запросы к ним идут через свой контакт или свою группу.
- Индексы: `contacts (user_id, name)` вместо `contacts_name_idx` - список всегда «мои, по имени»; `groups`: уникальный индекс `(user_id, translate(lower(name), 'ё', 'е'))` вместо общего - у разных пользователей названия могут совпадать.
- Все функции чтения получают `userId` первым параметром: `listContacts(userId, search, groupId)`, `countContacts(userId)`, `getContact(userId, id)`, `listNotes(userId, contactId)`, `listDueContacts(userId)`, `listGroups(userId)`, `listContactGroups(userId, contactId)`. Явный параметр видно в коде, и тесту легко передать A или B. `userId` берётся только из `getCurrentUser()`, никогда из того, что прислал браузер.
- Все серверные действия: `const user = await getCurrentUser()` и условие `user_id = user.id` в каждом `update`/`delete`/`insert ... select`. Чужая запись не находится - тот же ответ, что для несуществующей («Контакт не найден…», «Группа не найдена…»).
- Связь «контакт - группа»: вставка только если и контакт, и группа - мои (`insert ... select ... where contact.user_id = me and group.user_id = me`). `setContactGroups` берёт из присланных `groupIds` только мои группы - чужие пропускаются, как удалённые. `findOrCreateGroup` ищет и создаёт группу только среди моих.
- Фильтр по группе в адресе: `resolveGroupFilter` уже сверяет id со списком групп - список теперь только мой, поэтому чужая группа превращается в «Все группы» без новой логики. Условие фильтра в `listContacts` тоже проверяет владельца группы.
- Карточка чужого контакта: `getContact` вернёт `null` → `notFound()` → существующая страница «Такого контакта нет».

Отвергнуто: защита строк на уровне Postgres (Row Level Security) - надёжно, но требует передавать пользователя в каждое соединение с базой; для одного приложения с одним слоем запросов - лишняя сложность. Составные внешние ключи, запрещающие связь контакта и группы разных владельцев на уровне базы, - тоже лишняя сложность при одном месте вставки связей, которое покрыто тестами.

### 9. Готовые группы у нового пользователя

`databaseHooks.user.create.after` в настройках Better Auth: после создания пользователя (первый вход по ссылке) - вставить ему «Семья», «Друзья», «Коллеги». Срабатывает один раз на пользователя, поэтому удалённая группа при следующих входах не возвращается. Пользователь-владелец, которого создаёт миграция (решение 10), этот обработчик не проходит - его готовые группы уже есть из `0003`.

### 10. Миграции: таблицы входа и передача данных владельцу

- `0004` (генерирует `pnpm db:generate`): таблицы `users`, `sessions`, `accounts`, `verifications`, `sign_in_emails`; столбцы `user_id` у `contacts` и `groups` - пока без `not null`.
- `0005` (своя, `drizzle-kit generate --custom`) - **меняет существующие данные**, показать владельцу до merge:
  1. Если в `contacts` или `groups` есть строки: взять почту владельца из `current_setting('app.owner_email', true)`; пустая или не похожа на почту - `raise exception` с понятным текстом, транзакция откатывается, ничего не меняется.
  2. Создать пользователя с этой почтой (маленькими буквами, `email_verified = true` - иначе Better Auth при первом входе сочтёт почту неподтверждённой), если его ещё нет.
  3. `update contacts set user_id = <владелец> where user_id is null`, то же для `groups`. Заметки и связи не трогаются.
  4. `user_id` → `not null`, заменить индексы (решение 8).
- Как почта попадает в SQL: `scripts/migrate.mts` подключается одним клиентом (`pg.Client`), выполняет `select set_config('app.owner_email', $1, false)` с `OWNER_EMAIL` и затем применяет миграции тем же клиентом. Почта уходит параметром запроса, не склеивается в текст SQL.
- Локальный `pnpm db:migrate` переходит с drizzle-kit на тот же скрипт: `node --env-file-if-exists=.env scripts/migrate.mts` - одинаково локально, в CI и на сервере. `test/global-setup.ts` и `test/migrations.ts` тоже передают почту (тестовую).
- `deploy/compose.yaml`: контейнеру `migrate` - `OWNER_EMAIL`, приложению - `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL`, `SMTP_*`, `MAIL_FROM_ADDRESS`. Обязательные - через `${VAR:?...}`: без строки в `.env` выкатка падает на первом же шаге, до бэкапа, и работает прошлая версия.

Отвергнуто: почта прямо в тексте миграции - публичный репозиторий (решение владельца). Передача данных при первом входе владельца («ничьё - первому, кто войдёт с этой почтой») - данные висели бы без владельца, а `user_id` нельзя было бы сделать `not null`.

### 11. Демо-данные

`pnpm db:seed` (по-прежнему только если контактов нет): найти или создать пользователя `OWNER_EMAIL` (`email_verified = true`), его контактам и заметкам - `user_id` владельца, раскладка по группам - по готовым группам владельца. Без `OWNER_EMAIL` - понятная ошибка. Скрипт читает `.env` как сейчас.

### 12. Автотесты

- Vitest: текущий пользователь в серверных действиях - подмена модуля `@/lib/auth/current-user` (как уже подменяются `next/cache` и `next/server`): тест сам выбирает, кто «вошёл», A или B. Всё остальное настоящее, включая базу. Сам `getCurrentUser()` и Better Auth проверяются отдельными тестами через настоящий обработчик `auth.handler(new Request(...))`: запрос ссылки, письмо в Mailpit, переход по ссылке, cookie, выход, продление срока (срок в `sessions` сдвигается прямо в базе - не ждать 30 дней), лимит (время в `sign_in_emails` сдвигается прямо в базе).
- Фабрики `test/factories.ts`: `givenUser(email)`, у `givenContact` и `givenGroup` - обязательный владелец.
- Playwright: помощник `signIn(page, email)` - открыть `/login`, ввести почту, взять ссылку из Mailpit, открыть. Проект `setup` входит под `OWNER_EMAIL` и сохраняет вход в файл (`storageState`), все старые e2e работают под владельцем; их прямые SQL-вставки получают `user_id` владельца. Новый `e2e/sign-in.spec.ts` - без сохранённого входа: главный сценарий входа, A и B, выход, «Ссылка устарела», неверный адрес, шапка.
- Главный сценарий (`e2e/main-scenario.spec.ts`) остаётся отдельным; шаг «другой браузер» теперь сначала входит под тем же владельцем, потом видит те же контакты.
- Каждый сценарий спек - свой тест с тем же названием. Сценарии «Письмо на сервере» и «Отправитель на сервере» - проверка руками после выкатки (сервер без автотестов по CLAUDE.md).

### 13. nginx передаёт адрес устройства

- В нашем блоке `server` для `app.personalcrm.site` в `/etc/nginx/sites-available/personalcrm.conf` должна быть строка `proxy_set_header X-Real-IP $remote_addr;`. nginx записывает в неё адрес, с которого к нему пришли, и заменяет то, что мог прислать сам браузер, - подделать адрес нельзя. Там же - `X-Forwarded-For $proxy_add_x_forwarded_for` и `X-Forwarded-Proto $scheme`, если их нет.
- Это свой файл на общем сервере: правим только блок приложения, лендинг и чужие настройки не трогаем (CLAUDE.md). Перед правкой - копия файла, после - `nginx -t` и `systemctl reload nginx`.
- Файл живёт только на сервере, не в репозитории; изменение записывается в README в разделе о сервере.
- Нужен доступ к серверу: агент выполняет шаг только с разрешения владельца или даёт ему команды.

Отвергнуто: брать первый адрес из `X-Forwarded-For` - его может подделать сам браузер, nginx только дописывает к нему свой.

## Risks / Trade-offs

- [Better Auth поменяет формат записи ссылки, и «новая отменяет старые» молча перестанет работать] → тест «Запросил новую ссылку» на настоящем Better Auth; версия библиотеки зафиксирована в `pnpm-lock.yaml`.
- [Продление срока в `proxy.ts` не перенесёт cookie (поведение `nextCookies` вне серверного действия)] → тест продления; запасной путь - маленький компонент в шапке, который при открытии страницы запрашивает `/api/auth/get-session` из браузера (так Better Auth продлевает cookie штатно). Если не выйдет и он - остановлюсь и обсужу.
- [Пропущенное условие `user_id` в одном запросе откроет чужие данные] → у каждой функции чтения и каждого действия тест «B не видит / не меняет данные A»; `userId` - обязательный параметр, забыть его нельзя без ошибки типов.
- [Миграция `0005` на проде упадёт или не дотянет данные] → она в одной транзакции; бэкап базы снимается перед миграциями; тест миграции на копии данных проверяет, что количество контактов, заметок, групп и связей не изменилось; после выкатки - сверка количеств руками (README).
- [Без строк в `.env` на сервере выкатка упадёт] → она падает до бэкапа и миграций, работает прошлая версия; список строк - в задачах владельца до merge.
- [Письма от нового домена попадут в спам или Resend их не примет] → домен подтверждается в Resend записями DNS до выкатки (SPF, DKIM); проверка руками - письмо в настоящий ящик.
- [Каждое открытие страницы - лишний запрос к базе в `proxy.ts`] → только для запросов документа, не для фоновых подгрузок; для маленького приложения незаметно.
- [nginx не передаёт `X-Real-IP` - приложение видит всех с адреса Docker, и после 5 разных адресов в час вход останавливается у всех] → проверка и правка nginx до выкатки (решение 13); после выкатки - проверка с двух разных сетей (задача 11.3).
- [Друзья в одной домашней сети делят лимит в 5 адресов в час] → решение владельца; на практике в одной сети редко входят больше 5 разных людей за час.
- [Владелец при ручной проверке на своём компьютере упрётся в 5 придуманных адресов в час] → в README: так и должно быть, подождать час.
- [Адрес устройства - личные данные] → хранится только в журнале и не дольше часа.

## Migration Plan

До merge (владелец, задачи с пометкой «(владелец)» в tasks.md):

1. Завести аккаунт Resend, добавить домен `mail.personalcrm.site`, внести его записи DNS у регистратора, дождаться «Verified».
2. Создать ключ Resend с правом только на отправку.
3. Добавить в `/opt/personal-crm/.env` на сервере строки: `OWNER_EMAIL`, `BETTER_AUTH_SECRET`, `BETTER_AUTH_URL=https://app.personalcrm.site`, `SMTP_HOST=smtp.resend.com`, `SMTP_PORT=465`, `SMTP_USER=resend`, `SMTP_PASSWORD=<ключ Resend>`, `MAIL_FROM_ADDRESS=noreply@mail.personalcrm.site`. Права файла остаются 600.
4. Посмотреть миграцию `0005` (она меняет данные) и согласиться.
5. Проверить и при необходимости дополнить nginx (решение 13) - агент с вашего разрешения или вы по его командам.

Выкатка - как обычно: merge → образ → бэкап базы → миграции `0004`, `0005` → новый образ → smoke `/health`. После - проверить руками: вход владельца по настоящему письму, все прежние контакты на месте (число «Всего N» как до выкатки), второй пользователь видит пустой список.

Откат - только вместе и только вручную (запускает владелец, порядок - в README):

1. Вернуть прошлую версию приложения: `deploy.sh <прошлый тег>`. Прошлая версия не умеет заполнять `user_id`, поэтому до шага 2 добавление контактов у неё не работает.
2. Восстановить базу из бэкапа, снятого перед выкаткой входа (`backups/deploy_<время>_<прошлый тег>.dump`), скриптом `restore.sh` - он поднимет ту же, уже прошлую, версию приложения.
3. Всё, что добавили после выкатки входа, при откате пропадает - бэкап снят до неё.

Локально после получения изменений: добавить новые строки в `.env` (список - в README и `.env.example`), `docker compose up -d` (поднимет Mailpit), `pnpm install`, `pnpm db:migrate`.
