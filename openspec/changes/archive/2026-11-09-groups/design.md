# Design

## Context

Зачем фича - см. proposal.md, что должно работать - `specs/contact-groups/spec.md`.

Макет экранов (компьютер и телефон), согласован владельцем: https://claude.ai/artifact/7fAzswu9it8jsTJFQ9EmKY - главная с фильтром и плашками групп, карточка со списком групп, форма с полем «Группы», страница «Группы» (создание, переименование), вопрос об удалении. Вёрстка плашек, фильтра и списков - по нему; цвета и шрифты - токены приложения. Ссылка открывается только у владельца, пока её не расшарили.

Как устроено сейчас (то, на что опирается подход):

- В базе две таблицы: `contacts` и `notes`. Схема - `src/db/schema.ts`, миграции генерирует drizzle-kit в `drizzle/` (сейчас `0000`, `0001`). На сервере миграции применяет разовый контейнер до старта нового образа.
- Чтение данных - функции в `src/lib/contacts/queries.ts` (`listContacts(search)`, `getContact`, `listDueContacts`, `listNotes`), запись - серверные действия в `src/app/contacts/actions.ts`. Действия проверяют ввод через zod (`src/lib/contacts/validation.ts`), возвращают `ActionResult` (успех или текст ошибки на русском) и вызывают `revalidatePath`, чтобы экраны обновились.
- Главная (`src/app/page.tsx`) рисует весь список одной таблицей - в тестовой базе 1000 контактов. Поиск хранится в адресе страницы (`?q=`), компонент `ContactSearch` меняет адрес через `router.replace` и сохраняет остальные параметры адреса.
- В карточке частота общения меняется без формы: `ContactFrequencyPicker` на `Select` из shadcn/ui (Base UI), сразу показывает выбор (`useOptimistic`) и откатывает его с сообщением, если сохранить не удалось.
- Тестов на Vitest нет, Vitest не установлен. Есть e2e на Playwright, они ходят в рабочую локальную базу. Проверок на PR в GitHub Actions нет - только выкатка (`deploy.yml`).

## Goals / Non-Goals

**Goals:**

- Группы и связь «контакт - группа» хранятся в базе так, что повторить название группы нельзя даже при двух одновременных запросах.
- Список на главной с группами в строках открывается так же быстро, как сейчас, на 1000 контактов.
- В проекте появляется Vitest: тесты серверной части идут на отдельной тестовой базе в том же Docker и не трогают рабочие данные.
- У каждого сценария спеки есть тест на Vitest - для его серверной части или логики подсказок; что видно только на экране, проверяется руками (см. решение 8).

**Non-Goals:**

- e2e-тесты для групп и проверки в CI - отдельной работой позже. Существующие e2e не трогаем, только прогоняем как проверку, что ничего не сломали.
- Поиск по названию группы, группы в блоке «Пора связаться», цвета и значки групп, ручной порядок групп, добавление в группу сразу нескольких контактов.

## Decisions

### 1. Данные: таблица групп и таблица связей

- `groups`: `id` (uuid), `name` (текст), `created_at`, `updated_at`.
- `contact_groups`: `contact_id` → `contacts.id`, `group_id` → `groups.id`, обе связи с `on delete cascade`; первичный ключ - пара (`contact_id`, `group_id`), поэтому контакт не может попасть в одну группу дважды; отдельный индекс по `group_id` - для фильтра.
- Уникальность названия - уникальный индекс по выражению `translate(lower(name), 'ё', 'е')`: то же правило, что уже работает в поиске. Его проверяет сама база, поэтому два одновременных «Создать группу «Теннис»» не дадут двух групп.
- `on delete cascade` с обеих сторон: удалили группу - пропали только её связи; удалили контакт - пропали его связи, группы остались. Отдельного кода для этого не нужно.

Отвергнуто: список названий групп прямо в `contacts` (массив текста) - переименование и удаление группы пришлось бы переписывать в каждом контакте, а база не следила бы за целостностью. Название как ключ группы - переименование тоже трогало бы все связи.

### 2. Миграции: таблицы и готовые группы отдельно

- `0002`: генерирует `pnpm db:generate` по схеме - только создание двух таблиц и индексов.
- `0003`: пустая миграция `drizzle-kit generate --custom`, в ней вставка «Семья», «Друзья», «Коллеги».

Каждая миграция выполняется в базе один раз (drizzle помнит применённые), поэтому удалённая или переименованная готовая группа при следующих выкатках не возвращается. Существующие контакты и заметки миграции не трогают.

Отвергнуто: создавать готовые группы в коде приложения, «если групп нет» - удалил все группы, и они вернулись бы. В `pnpm db:seed` - на сервере seed не запускается.

### 3. Серверный код групп

- `src/lib/groups/validation.ts`: схема названия (обрезать пробелы, не пусто, не длиннее 50) и `normalizeGroupName` - то же приведение, что в индексе, для подсказок в браузере.
- `src/lib/groups/queries.ts`: `listGroups()` - все группы по алфавиту с числом контактов; `listContactGroups(contactId)` - группы контакта по алфавиту.
- `listContacts(search, groupId?)` в `src/lib/contacts/queries.ts`: у каждой строки - её группы (`id`, `name`) одним запросом, через вложенный подзапрос со сбором в JSON; при `groupId` - только контакты этой группы, вместе с условием поиска. Так нет отдельного запроса на каждую строку.
- `src/app/groups/actions.ts`: `createGroup(name)`, `renameGroup(id, name)`, `deleteGroup(id)` - для страницы «Группы»; `addContactToGroup`, `removeContactFromGroup`, `createGroupForContact(contactId, name)` - для карточки. Отметка в карточке шлёт одно «добавить» или «убрать», а не весь набор групп: две быстрые отметки не перезапишут друг друга.
- «Найти или создать» (`createGroupForContact`, новая группа из формы): вставка с `on conflict` по уникальному индексу, затем взять группу по приведённому названию - так при совпадении берётся существующая.
- `createGroup` и `renameGroup` при совпадении названия возвращают «Группа «Друзья» уже есть» - с написанием существующей группы, а не введённым. Переименование группы в своё же название с другими буквами («теннис» → «Теннис») индекс пропускает: это та же строка.
- Группа, которую уже удалили в другой вкладке: переименование и удаление отвечают «Группа не найдена — возможно, её уже удалили.»; добавление контакта в неё ничего не ломает и не создаёт её заново.
- Обновление экранов: действия с контактом обновляют `/`, `/groups` и его карточку; переименование и удаление группы касаются всех карточек, поэтому обновляют всё приложение (`revalidatePath("/", "layout")`).
- Тексты ошибок - в `src/lib/groups/messages.ts`, как `src/lib/contacts/messages.ts`: их показывает и браузер.

### 4. Группы в форме контакта

- В значения формы добавляются `groupIds` (выбранные существующие группы) и `newGroupNames` (вписанные новые). Пока форма открыта, новые группы живут только в ней - поэтому закрытие без сохранения ничего не оставляет.
- `createContact` и `updateContact` в одной транзакции сохраняют контакт, находят или создают новые группы и приводят связи к выбранному набору (убрать лишние, добавить недостающие). Ошибка в названии новой группы - ошибка поля «Группы», и не сохраняется ничего.
- Выбранная группа, которую тем временем удалили, при сохранении просто пропускается: связь вставляется только с группами, которые есть в базе.

### 5. Выбор групп в интерфейсе

- Компонент выбора с вводом и несколькими значениями - combobox из shadcn/ui (`pnpm dlx shadcn@latest add combobox`) на Base UI, который уже в проекте. Новых зависимостей быть не должно - проверяется по `package.json`.
- Что предлагать при вводе, решает чистая функция `groupSuggestions(query, groups)`: подходящие группы и, если точного совпадения по приведённому названию нет, пункт «Создать группу «…»». Её легко проверить тестом без браузера.
- Форма: поле «Группы» последним, после «Как часто общаться»; выбранные группы - плашки внутри поля.
- Карточка: в шапке рядом с частотой - плашки групп или кнопка «Добавить в группу»; нажатие открывает список с полем ввода и отметками. Как у частоты: выбор виден сразу (`useOptimistic`), при ошибке откатывается с сообщением «Не удалось сохранить…», список не закрывается после отметки.
- Точный вид, место на телефоне и цвета - по макету (задача 1), только дизайн-токены.

### 6. Главная: группы в строках и фильтр

- Группы в строке - маленькие плашки под именем, в ячейке «Имя»; стили задаются один раз на таблицу, как сейчас, чтобы 1000 строк не тяжелели.
- Фильтр - `Select` «Все группы» и группы по алфавиту рядом с поиском. Выбор пишется в адрес `?group=<id>` через `router.replace`, параметр `q` сохраняется; поиск так же сохраняет `group`. Поэтому фильтр переживает обновление страницы и открывается в другом браузере.
- Страница сверяет `group` из адреса со списком групп (чистая функция): неизвестная или удалённая группа - то же, что «Все группы».
- Счётчик «Найдено: N контактов из M», если задан поиск или группа; пустая группа без поиска - «В группе «Теннис» пока никого нет», с поиском - прежний текст «Никого не нашлось…».
- Блок «Пора связаться» фильтр не читает - запрос `listDueContacts` не меняется.

### 7. Страница «Группы»

- Адрес `/groups`, ссылка «Группы» в шапке главной рядом с «Добавить контакт», кнопка «Все контакты» назад - как в карточке.
- Серверная страница со списком; «Создать группу» и «Переименовать» - поле прямо в строке списка с кнопками «Создать»/«Сохранить» и «Отмена»; «Удалить» - диалог подтверждения, как у удаления контакта, после удаления сообщение «Группа удалена».
- Название группы - ссылка на `/?group=<id>`. Число контактов - через существующий `pluralize`.

### 8. Тесты: Vitest на отдельной тестовой базе

- Vitest (последняя стабильная версия - проверить при установке), команда `pnpm test`. Тестовые файлы - рядом с кодом, `*.test.ts`. Файлы идут по очереди, не параллельно: у них одна база.
- Тестовая база - `<имя рабочей базы>_test` в том же Postgres в Docker. Перед прогоном она пересоздаётся и получает все миграции; адрес выводится из `DATABASE_URL`, новых строк в `.env` не нужно. Перед каждым тестом таблицы очищаются. Рабочая база не меняется.
- Тесты миграций (готовые группы, старые контакты, удалённая группа не возвращается) создают ещё одну временную базу и применяют миграции по шагам: сначала до `0001`, потом остальные.
- Сценарии «База данных недоступна» - отдельный тестовый файл, где адрес базы указывает на закрытый порт: настоящий сбой соединения, базу не подменяем.
- База в тестах настоящая. Подменяются только вызовы Next.js, которым нужен живой запрос к сайту: `revalidatePath`, `connection()` и защита `server-only`. Поэтому обновление экранов после действий тесты не видят - его проверяем руками.
- Каждый сценарий - свой тест, названный как сценарий. Сценарии только про экран проверяются руками по README, а тесты для них появятся вместе с e2e: «Форму закрыли без сохранения», «Отмена» у переименования, «Передумал» у удаления, «Передумал создавать», «Переход к людям группы». У «Фильтр в адресе страницы» тестом проверяется разбор адреса, у «Пора связаться не меняется» - что блок по-прежнему показывает Аню.

### 9. Тестовые данные

`pnpm db:seed` (только на пустой базе) после контактов раскладывает часть из них по готовым группам: примерно 3% в «Семья», 10% в «Друзья», 20% в «Коллеги», некоторые сразу в две; то же фиксированное зерно случайности. Нет готовой группы - её пропускает.

## Risks / Trade-offs

- [Главная тяжелеет: подзапрос групп и плашки на 1000 строк] → один запрос без отдельного на строку; плашки - простые элементы со стилями на таблице; проверка - главная на тестовых данных открывается так же быстро, как до фичи.
- [Combobox из shadcn/ui не умеет «создать новое» так, как нужно] → у Base UI есть пример такого выбора с созданием; если не выйдет - остановлюсь и обсужу замену, новую библиотеку сам не ставлю.
- [Большие и маленькие буквы кириллицы сравниваются по настройкам языка базы] → то же уже работает в поиске; тесты «Такое название уже есть» («друзья» и «Друзья») и «Ёлка»/«Елка» поймают расхождение.
- [Подмена `revalidatePath` в тестах прячет забытое обновление экрана] → ручная проверка сценариев: после действия экран меняется без F5.
- [Тесты требуют запущенной базы в Docker] → понятная ошибка «Запустите базу: docker compose up -d» вместо падения непонятным текстом.
- [Отдельный файл со «сломанной» базой может взять общее соединение из соседнего файла] → Vitest изолирует файлы; тест сначала проверяет, что соединение действительно не работает.

## Migration Plan

1. Merge в main → CI собирает образ → на сервере разовый контейнер применяет `0002` (таблицы) и `0003` (готовые группы) → стартует новый образ → smoke `/health`.
2. Откат - вручную, запускает владелец: предыдущий образ работает с новыми таблицами в базе, он их просто не читает. Откатывать базу не нужно.
3. Локально после получения изменений - `pnpm db:migrate`.
