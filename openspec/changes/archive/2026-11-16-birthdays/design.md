# Design

## Context

Что есть сейчас (зачем это нужно - см. `proposal.md`, требования - `specs/birthdays/spec.md`):

- Таблица `contacts` (`src/db/schema.ts`): имя, «кто это», «откуда знакомы», телефон, почта, частота общения. Схема и миграции - Drizzle, миграции в `drizzle/`, последняя - `0005_assign_owner.sql`.
- Форма контакта (`src/components/contact-form.tsx`) - общая для добавления и изменения. Значения собирает `readContactForm`, отправляет серверное действие `createContact` / `updateContact` (`src/app/contacts/actions.ts`). Проверка - `contactInputSchema` (zod, `src/lib/contacts/validation.ts`) - выполняется на сервере; ошибки возвращаются по полям. Ошибки двух полей групп уже сводятся в одно поле «Группы» - тот же приём подойдёт для трёх частей даты.
- Выбор частоты в форме - компонент `Select` (shadcn/ui на Base UI) со скрытым полем `name`, его значение попадает в `FormData`.
- Главная (`src/app/page.tsx`): `ContactList` в одном `Promise.all` читает список, счётчик, «Пора связаться» (только когда поиск пуст) и группы. Блок «Пора связаться» - клиентский компонент `KeepInTouchList`, тексты строк готовит сервер. «Первые пять и «Показать всех»» - функция `dueBlockView` (`src/lib/contacts/due-block.ts`), она уже обобщённая.
- Карточка (`src/app/contacts/[id]/page.tsx`): под именем - «Кто это», ниже частота и кнопка «Связались», группы.
- Время: в контейнере приложения часовой пояс не задан - это UTC. Даты заметок и «В списке с» форматируются по UTC. «Пора связаться» считает срок по часам базы (`now()`).
- `revalidatePath("/")` уже вызывается в `createContact` и `updateContact`: после сохранения формы главная читается заново.
- Макет экранов (согласован владельцем 2026-11-16): https://claude.ai/artifact/CHo1TcD1royhDJoL7XGHPC - главная, карточка и форма «Изменить» для компьютера и телефона.
- Тесты: Vitest на настоящей базе (`test/factories.ts` - готовые данные), Playwright сквозные (`e2e/`, данные готовят SQL-запросами). Имена тестов совпадают с названиями сценариев спеки.

## Goals / Non-Goals

**Goals:**

- Все правила календаря - ближайший день рождения, 29 февраля, возраст, «сегодня по Москве» - в одном модуле без обращения к базе, чтобы проверять их тестами с любой «сегодняшней» датой.
- Изменение схемы только добавляет поля: прошлый образ приложения работает с новой базой, ручной откат образа безопасен.
- Блок выглядит и ведёт себя как «Пора связаться» и переиспользует его части.

**Non-Goals:**

- Переводить на московское время остальные даты приложения (заметки, «В списке с», «Пора связаться») - см. Risks.
- Поиск, фильтр или сортировка общего списка по дате рождения.
- Индекс в базе под дни рождения - не нужен при нынешних объёмах (решение 3).

## Decisions

### 1. Данные: три необязательных поля в `contacts`

- `birth_day` - день, `smallint`, 1-31;
- `birth_month` - месяц, `smallint`, 1-12;
- `birth_year` - год, `smallint`, не раньше 1900.

Все три пустые - даты нет. Проверки в самой базе (`check`): день и месяц либо оба пустые, либо оба заданы; год задан только вместе с ними; числа в своих пределах. Существует ли такая дата (31 апреля, 29 февраля 2023) и не в будущем ли она - проверяет приложение (решение 4): «сегодня» нельзя использовать в проверке базы, а сообщение для пользователя всё равно даёт приложение.

Почему не одно поле типа «дата»: у даты всегда есть год. Для «20 ноября без года» пришлось бы подставлять выдуманный год и отдельный флаг «год неизвестен» - выдуманный год легко случайно показать или посчитать в возрасте. Почему не текст «11-20»: база не проверит, что это дата, и с текстом неудобно считать.

Миграция - `pnpm db:generate` (Drizzle), файл `drizzle/0006_birthdays.sql`: только добавляет три пустых поля и проверки. Существующие строки не меняются, поэтому по правилам проекта показывать её до merge не обязательно - но она будет видна в PR.

### 2. Календарь - модуль `src/lib/contacts/birthdays.ts`

Без `server-only`: названия месяцев нужны и форме в браузере. Дата - простая тройка `{ year, month, day }` без часов и часового пояса, считать дни помогает `Date.UTC`, чтобы часовой пояс сервера ни на что не влиял.

- `moscowToday(now = new Date())` - сегодняшняя дата по Москве: `Intl.DateTimeFormat` с `timeZone: "Europe/Moscow"`. Параметр `now` нужен тестам («Полночь по Москве»: 16 ноября 21:30 UTC → 17 ноября).
- `birthdayIn(birthday, year)` - день рождения в данном году; 29 февраля в невисокосный год → 28 февраля.
- `nextBirthday(birthday, today)` - ближайший день рождения начиная с сегодня: дата и через сколько дней (0 - сегодня). Если год рождения известен, день рождения бывает только в годы после него - поэтому родившийся сегодня получает следующий день рождения через год.
- `ageOn(birthday, today)` - полных лет на дату; пусто без года. Возраст прибавляется в `birthdayIn` этого года - для 29 февраля в невисокосный год это 28 февраля, как и в блоке.
- `upcomingBirthdays(contacts, today)` - контакты, у которых до дня рождения 0-7 дней, отсортированные по числу дней. Сортировка стабильная, а контакты приходят из базы уже по имени - так при равенстве дней порядок по имени тот же, что в общем списке (база сравнивает имена по своим правилам, и повторять их в коде не нужно).
- `MONTH_NAMES` - «январь» … «декабрь» для списка в форме; константа, а не `Intl`, чтобы не зависеть от того, как браузер склоняет месяцы.

Тексты для экрана - в `src/lib/format.ts`, рядом с `formatOverdue`: «20 ноября», «20 ноября 1990 г.» (`Intl` с `timeZone: "UTC"` для даты из `Date.UTC`), «сегодня» / «завтра» / «через N дней», «исполнится N» / «исполняется N», «(35 лет)» через уже существующий `pluralize`.

### 3. Блок считается в приложении, а не в SQL

Новый запрос `listContactBirthdays(userId)` в `src/lib/contacts/queries.ts` читает у контактов пользователя с заданной датой только `id`, имя и три поля даты, по имени - как общий список. Отбор «скоро» и порядок - `upcomingBirthdays` из решения 2.

Почему не в SQL (например, восемь дат через `generate_series` и сравнение с днём и месяцем): правило 29 февраля и «сегодня по Москве» пришлось бы писать второй раз на SQL - для карточки они всё равно нужны в коде, - а тесты должны были бы подменять часы базы. Цена - главная читает по 4 коротких поля у контактов с датой: при 1 000 демо-контактов это меньше, чем общий список, который главная уже читает целиком. Если контактов станут десятки тысяч, отбор можно перенести в SQL, не меняя страницу.

Почему «сегодня» по часам приложения, а не базы, как у «Пора связаться»: дню рождения нужна только дата, приложение и база на одном сервере, а функция с параметром `now` проверяется тестом без подмены часов базы.

### 4. Проверка даты - внутри `contactInputSchema`

Форма отправляет одно поле `birthday: { day, month, year }` - три строки, пустая строка = не указано. Схема этого поля превращает его в `{ day, month, year | null }` или `null`. Ошибки любой части - под одним полем `birthday` («Дата рождения»), как у групп. Порядок проверок и тексты ошибок - из спеки («Проверка даты рождения»): сначала что заполнено (день и месяц вместе, год без них нельзя), затем год (четыре цифры, не раньше 1900), затем существует ли дата, последней - не в будущем ли она по `moscowToday()`. Проверка вложена в само поле, поэтому `contactInputSchema.shape.contactFrequency`, которым пользуется смена частоты из карточки, продолжает работать.

`createContact` пишет три поля даты; `updateContact` всегда перезаписывает все три, поэтому очищенные поля убирают дату. Отдельного серверного действия для даты нет - менять её можно только формой.

### 5. Поле в форме

Компонент `BirthdayField` (`src/components/birthday-field.tsx`): подпись «Дата рождения», в одну строку - день (`inputMode="numeric"`, до 2 знаков, подсказка «День»), месяц (`Select` как у частоты: «Не указан» и 12 месяцев) и год (`inputMode="numeric"`, до 4 знаков, подсказка «Год»). Ошибка - одна под всей строкой, все три части отмечены как ошибочные. У каждой части своё скрытое для глаз название для экранных чтецов: «День рождения: число», «месяц», «год».

Не `type="number"`: такое поле меняет значение от колёсика мыши и пропускает «e». Проверяет всё равно сервер.

Начальные значения для «Изменить» берутся один раз при открытии формы - по той же причине, что у частоты (комментарий в `FrequencyField`).

### 6. Карточка и главная

- Карточка: под «Кто это» строка «День рождения 20 ноября 1990 г. (35 лет)» со значком торта; возраст - `ageOn(birthday, moscowToday())` на сервере. Без даты строки нет.
- Главная: `listContactBirthdays` - в тот же `Promise.all`, что и «Пора связаться», и так же пропускается, пока идёт поиск. Блок `UpcomingBirthdaysList` (`src/components/upcoming-birthdays-list.tsx`) стоит над `KeepInTouchList`, в своей обёртке `Suspense` - по той же причине, что у «Пора связаться» (комментарий в `page.tsx`). Тексты строк готовит сервер, как у «Пора связаться», чтобы часовой пояс браузера их не менял.
- Вёрстка блока - как у «Пора связаться»: карточка со значком и заголовком, строки с аватаром, имя-ссылка накрывает всю строку. Кнопок в строке нет. Значки - `lucide-react` (`CakeIcon`), цвета и отступы - только токены.
- «Первые пять»: `dueBlockView` и `DUE_VISIBLE_AT_FIRST` переезжают из `src/lib/contacts/due-block.ts` в общий `src/lib/home-block.ts` под именами `homeBlockView` и `HOME_BLOCK_VISIBLE_AT_FIRST`, вместе с тестами; оба блока пользуются ими. Переезд не меняет поведение - тесты те же.

### 7. Демо-данные

`pnpm db:seed`: даты рождения разыгрываются последними, после групп - как частота, чтобы прежние демо-контакты, заметки и группы не изменились. Примерно у 60% контактов есть дата, у трети из них - без года, годы 1950-2005. При 1 000 контактов в ближайшие 7 дней попадает около десятка - блок виден сразу, и «Показать всех» тоже.

## Risks / Trade-offs

- [Сквозной тест создаёт день рождения «завтра по Москве», а полночь по Москве наступает до того, как страница прочитана] → тест падает раз в долгое время. Тесты берут даты от `moscowToday()` в момент подготовки данных; в CI окно - секунды. Если упадёт - перезапуск, причина в логе понятна.
- [Остальные даты приложения по-прежнему по UTC] → у заметки, написанной в 01:00 по Москве, в карточке вчерашнее число, а дни рождения уже по Москве. Это было и раньше и не входит в изменение; если мешает - отдельная правка.
- [Пользователь не в Москве] → новый день для блока наступает в полночь по Москве, а не по его часам. Так решил владелец; если пользователей в других поясах станет много, понадобится пояс в настройках пользователя.
- [Проверки в базе и в приложении разойдутся] → приложение проверяет строже базы, а база лишь не даёт записать явную бессмыслицу. Тест на миграцию проверяет, что база отклоняет день без месяца и месяц 13.
- [Старый образ после отката] → не знает о новых полях и просто не читает их; при сохранении формы в старой версии поля даты не трогаются (`UPDATE` перечисляет только свои поля), даты сохраняются.

## Migration Plan

1. Merge в main → образ → тест-стенд: миграция `0006_birthdays` (только добавляет поля) → новый образ → smoke `/health`.
2. Проверка на тест-стенде руками (шаги - в `tasks.md`, раздел Workflow follow-up): добавить дату, увидеть блок, карточку, ошибки формы.
3. Выкатку на прод запускает владелец через Deploy prod; перед миграцией - бэкап базы, как всегда.
4. Откат - Deploy prod с галочкой «откат»: прошлый образ работает с новыми полями. Удалять поля из базы не нужно.
